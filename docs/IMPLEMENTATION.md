# Homestock — implementation architecture (Rust)

This file adds the owner's implementation plan to the design spec in `DESIGN.md`. If the two disagree on **behaviour or UI**, `DESIGN.md` wins. This file decides **stack, schema, structure and operations**.

The implementation lives at the repository root (`src/`, `migrations/`, `templates/`, `static/`, `styles/`). Section references below point at the files that implement each part.

---

## 1. Stack

| Concern | Choice | Notes |
|---|---|---|
| Runtime | Rust (stable), `tokio` **current-thread** runtime | Lowest idle footprint. CPU-heavy work (image resize, backup, CSV) goes to `spawn_blocking`. |
| HTTP | `axum` 0.8, `tower-http` (static files, compression, body limit, trace) | Path syntax `/{id}`. |
| DB | SQLite via `rusqlite` (`bundled`, `backup` features), **WAL** | One writer connection behind a `Mutex`, used through `spawn_blocking`. Plenty for 2–6 users, and SQLite serialises writes anyway. |
| Templates | `askama` (compile-time) | Templates are checked at build time and shipped inside the binary. |
| Interactivity | **HTMX** (vendored `static/htmx.min.js`) + ~100 lines of vanilla JS (steppers, drag-and-drop, share) | No SPA. |
| CSS | Tailwind v4 via the **standalone Tailwind CLI** at build time (`scripts/build-css.sh`, pinned and checksum-verified) → `static/app.css` | No CDN, ever. See “Offline” below. |
| Auth | `argon2` hashes, random session token in an HttpOnly cookie, `sessions` table | |
| Search | SQLite **FTS5 `trigram`** table → candidate set → Rust re-rank with `strsim` | Handles typos like “batery”. See §5. |
| Images | `image` crate (jpeg/png/webp/heic-less) → resize to 1600 px, re-encode JPEG q82 | Re-encoding also strips EXIF/GPS. Files are content-addressed: `photos/<sha256>.jpg`. |
| CSV | `csv` crate | |
| Config | `config.toml` (serde + `toml`) | Configures the database path, data directory, and backup timing/local queue retention. |
| Backup | SQLite online backup API writes local pending copies; an LXC timer syncs them to NAS when available | See §6. |

Expected footprint: a single ~8–12 MB static binary, about 10–20 MB RSS when idle, effectively 0% CPU when idle. The only wakeup is a 60 s backup tick.

## 3. Schema

The full SQL is in `migrations/` (`0001_init.sql` onward). Decisions:

- **Adjacency list + recursive CTE** rather than a closure table. A household has hundreds to low thousands of locations, and a recursive CTE over an indexed `parent_id` returns in microseconds. Moving a box (with everything inside) is then a **single-row UPDATE**. With a closure table it would mean rewriting every ancestor/descendant pair. Cycles are rejected in the move transaction.
- Time is stored as unix seconds (`INTEGER`, `unixepoch()`), so no date crate is needed in queries.
- `item.notes` is the only free-text field (Quick add + item detail). There is no separate description field.
- `checkout` rows are deleted on return. No history table, per the owner's requirement.
- `shop` is a real table. The design needs To buy / Bought / Put away and free-text entries. The **Low stock** and **Used up** tabs are dynamic views over `item`.
- `user.theme` (`light|dark|system`) is persisted **per user**. `user.last_location_id` is the remembered Quick-add box.
- `item_fts` is a trigram FTS5 table maintained by **app code** (SQLite triggers cannot run the recursive CTE needed for `path`). Call `reindex(items)` after every item write and after moving a box (reindex its subtree).

## 4. Core logic (see `src/repo/*.rs`)

- `subtree_ids(loc)` / `path(loc)`: recursive CTEs.
- `child_box_stats(parent)`: one CTE returns, for each child box, its recursive item count and box count (feeds “4 items · 1 box” and variant-B tiles).
- `items_in(loc, nested)`: items + `in_use` + tags in one query; consumed items sort last.
- `move_location(id, new_parent)`: cycle check → UPDATE → reindex subtree.
- `move_item(id, to, qty)`: whole-record move, or **split** + **merge** into a same-name, same-unit item at the destination. Splits are limited to `available`.
- `checkout(item, qty, user)`: transaction checks `available` (and a trigger guards it too).
- `put_away(checkout, to)`: moves the record if the checkout covers all of it, otherwise splits. Then deletes the checkout.
- `consume(item | checkout, qty, add_to_list)`: `qty = max(0, qty − n)`; `INSERT OR IGNORE` into `shop` (partial unique index = one open entry per item).
- `restock(shop_id, to?)`: linked → `qty += n`; unlinked → create/merge at `to`.

## 5. Fuzzy search (see `src/search.rs`)

1. Tokenise the query (lowercase, split on whitespace, strip `#`).
2. **Candidates:** for tokens ≥ 3 chars, OR together their trigrams in an FTS5 MATCH (`"bat" OR "ate" OR "ter" …`), limit 400. For shorter tokens, use `LIKE '%x%'` on `name`/`tags` (fast at this size). For an empty query with filters, all items.
3. **Re-rank in Rust:** split name, notes, tags and path into words. Every token must hit a word: prefix 4 / substring 3 / Levenshtein ≤1 (len ≥ 4) or ≤2 (len ≥ 6) → 2. Sort by score, then name.
4. Apply tag and status filters (`in_use`, `low`, `used`) in SQL on the candidate join.
5. HTMX: `hx-get="/search/results" hx-trigger="input changed delay:300ms, search" hx-indicator="#search-skeleton"`.

## 6. Backups (see `src/backup.rs`)

- `activity.rs` middleware stores the timestamp of the last request in an `AtomicU64`.
- The backup task keeps its **own read connection** and polls `PRAGMA data_version`. That value changes whenever *another* connection commits, so it is a free “dirty” flag with no app bookkeeping.
- The task captures an initial `data_version` baseline at startup. Opening/restarting the app by itself does not count as a database change; only commits after the baseline mark it dirty.
- Every 60 s a backup runs when **dirty AND idle ≥ `idle_secs` (default 300) AND since-last ≥ `min_interval_secs` (1800)**. It also runs when **dirty AND since-last ≥ `max_interval_secs` (86400)**, even if the app is busy. On graceful shutdown, it runs immediately only if the database is dirty.
- **Schema version:** SQLite's `PRAGMA user_version` is the schema version, currently `2`. Each migration sets it to its new version. On startup, if an existing database is behind the application schema, the app creates and integrity-checks an SQLite online backup next to the database (named `*.pre-migration-v<old>-to-v<new>-<timestamp>.sqlite3`) before applying any migration. If the backup cannot be completed and verified, startup stops before migration. New databases are initialized without a pre-migration backup.
- **Local pending backups:** the app writes a complete online SQLite backup under `data_dir/staging`, verifies it with `PRAGMA quick_check`, and keeps the newest three pending copies. This is independent of NAS availability, so Docker and Homestock can start normally.
- **NAS sync:** a separate LXC systemd timer checks the backup mount and sentinel every five minutes. It copies completed pending files to a temporary NAS filename, syncs and renames them, then removes the local pending copy. If the NAS is unavailable, pending files remain locally; when three are already queued, the oldest is pruned as a new one is created.
- **Photos and retention:** the sync timer copies missing content-addressed `photos/*.jpg` and prunes NAS database backups to the newest 48. The mount check and sentinel are enforced by the LXC-side sync process, not by the app container.
- Restore: stop the service, copy a backup to the configured `database_path`, delete its `-wal`/`-shm` sidecars, start.

- Full page if `HX-Request` is absent, otherwise the partial.

## 8. Front-end behaviour notes

- **Theme:** `<html data-theme="{{ user.theme }}">` is rendered by the server. The toggle does `hx-post="/me/theme"` and flips the attribute immediately in JS. Before login, use `prefers-color-scheme`. *(This replaces the DESIGN.md localStorage note.)*
- **Quick add (variant A):** the form posts multipart, so photo, name, qty, unit, min_qty, tags, keep_tags and notes all go in one request. On success the client:
  - resets name, qty, photo, min and notes;
  - keeps the tags if keep_tags is ticked;
  - refocuses the name field.
  Enter in name or unit submits; Enter in notes adds a newline. Cancel/Done just clears `#sheet`, and the server has already saved each row.
- **Remembered breadcrumb:** the lock is the `{id}` in the URL. Every quick-add POST also stores `user.last_location_id`, so the global + opens on the last box used.
- **Drag & drop** (`static/app.js`, ≥ 640 px only): native HTML5 DnD on `[data-drag-loc]` / `[data-drag-item]`. Drop targets are `[data-drop-loc]` (cards, breadcrumb, sidebar). Drop → `htmx.ajax('POST', …/move, {values, target:'#contents'})`. The server re-renders contents and returns the toast via OOB.
- **Share list:** `fetch('/shopping/share.txt')` → `navigator.share({title, text})`. On a non-abort failure, open the fallback sheet (Email `mailto:` + Copy text).

## 9. Deployment

- **Guides:** [`QUICKSTART.md`](QUICKSTART.md) (install), [`PROXMOX-LXC.md`](PROXMOX-LXC.md), [`HAPROXY.md`](HAPROXY.md) and [`ADMINISTRATION.md`](ADMINISTRATION.md) (upgrades, account recovery, backups, NAS copy).
- **Releases:** publishing a GitHub release (tag `v1.2.3`) runs `.github/workflows/release.yml`. It builds the image natively for amd64 and arm64, pushes one multi-arch image to `ghcr.io/<owner>/<repository>` with semantic-version and commit-SHA tags, signs it with keyless cosign, and attaches the signed install files (deployment bundle with the image pinned by digest, `install.sh` bootstrap, `SHA256SUMS`) to the release; see `deploy/README.md`. The app image itself makes no external requests at runtime.
- **Install and upgrade:** `install.sh` verifies the release bundle with cosign and runs `deploy/homestock-installer.sh`, which is idempotent: it writes `install.conf` (the source of truth) and generates `.env`, creates the data and certificate directories and a self-signed certificate, writes `config.toml` only if it is missing, and starts Compose. When the image changes under an existing database it stops the app, takes an integrity-checked backup into `<data>/pre-upgrade/`, starts the new image, and rolls back automatically if `/healthz` does not come up. The installer leaves `homestock-upgrade` (a copy of `install.sh` for this install), `homestock-admin`, `homestock-nas` and `homestock-doctor` on `PATH`. The config's `database_path` must stay under `/var/lib/homestock`, the container side of the data mount.
- **Access and HTTPS:** Homestock serves HTTPS directly on `8443` using PEM certificate/key paths in `config.toml`, mounted read-only from the host cert directory. Keep `cookie_secure = true`. A self-signed certificate encrypts traffic but is not trusted by browsers. HTTPS also provides the secure context required by `navigator.share`. Two setups work: serve a trusted certificate directly, or put a TLS-offloading reverse proxy (e.g. HAProxy on OPNsense with ACME) in front and re-encrypt to the app's own certificate. Behind a proxy, list its address in `trusted_proxies` so per-client limits use the address from its `X-Forwarded-For`, and firewall the app port so only the proxy can reach it.
- **Backup destination:** Homestock writes complete database backups to `<data>/staging` and stays available without NAS access. `homestock-nas` sets up a systemd timer (running `deploy/sync-homestock-backups.sh` as UID 10001) that copies pending backups and photos to an existing mounted folder or an rclone SMB mount, but only when the `.homestock-nas` sentinel exists there; `homestock-nas confirm` writes it after a person has checked the share is really mounted.
- **Permissions:** the container runs as UID/GID 10001; the installer creates a matching `homestock` user and group on the host so the sync service can run as it. These IDs are regular account IDs, not Debian system-account IDs.
- **SQLite pragmas** (set on every connection): `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`, `temp_store=MEMORY`, `cache_size=-4000` (≈4 MB). Run `PRAGMA optimize` after each backup.

## Local testing

For local HTTP testing, first build the stylesheet with `scripts/build-css.sh` (rerun it after changing templates or `styles/input.css`, or pass `--watch` to keep it rebuilding), then run `cargo run -- --config config.local.example.toml` and open `http://127.0.0.1:8080`. Create the initial household admin on the setup screen. This config stores test data under `/tmp/homestock-local-data`, binds only to loopback, and disables the Secure cookie flag because the connection is plain HTTP. Use `cookie_secure = true` behind HTTPS; do not expose the local config on a network.

## Documentation screenshots

The images in `docs/images/` are generated, not hand-made. After changing the UI, run `scripts/screenshots/run.sh` to retake them all. It builds the image from the checkout (or pass an image name to skip the build), starts it with a throwaway database, creates the admin through the setup screen, loads a demo household with `demo-data.py`, and captures each screen in headless Firefox with `shoot.mjs` (Puppeteer, pinned in `package-lock.json`). It needs Docker, Node with npm, Python 3, curl and Firefox. The demo data writes to SQLite directly, so it also rebuilds the search index the way `repo::items::reindex` does; if the schema changes, update `demo-data.py` with it. To add a screenshot, add a `shot(...)` line to `shoot.mjs` and reference the new file from the docs.
